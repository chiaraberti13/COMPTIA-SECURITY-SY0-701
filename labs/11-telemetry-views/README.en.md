# Lab 11 — Three sensors, one incident: network, identity and endpoint

| Field | Value |
|---|---|
| SY0-701 objectives | 4.4, 4.9 |
| Risk | `low` |
| Duration | 40 minutes |

The incident from Lab 03, a successful SSH brute force followed by an account created to stay,
told by three different sensors: network flows, the identity system's logs and the endpoint
agent. You query each source on its own, find out what it sees and what it misses, then merge
them into one timeline and write a correlation rule, as a SIEM does. You work on synthetic
files only, read-only.

## Scenario

Kestrelia's `web01` server (`10.0.0.5`) sends its telemetry to the SIEM from three sensors. The
security manager wants to know whether three are really needed, or whether one would be enough
to rebuild the incident of 29 September. You answer with the data: what each one sees, where it
is blind, what you get only by putting them together.

## Prerequisites

- Linux, macOS or WSL with `jq` 1.6 or later and `sha256sum` (on macOS `shasum -a 256`).
- The cloned repository: the telemetry is in `labs/11-telemetry-views/data/`.
- Knowledge: monitoring tools and sources (objective 4.4) and data sources supporting an
  investigation, that is network, system and endpoint logs (4.9). Lab 03 helps, but is not
  required.

## Topology

```text
[web01 10.0.0.5] ──► data/rete.jsonl      (network sensor: flows, like NetFlow or Zeek)
                 ──► data/identita.jsonl  (identity system: successful and failed logins)
                 ──► data/endpoint.jsonl  (EDR agent: processes and modified files)
[terminal with jq] ── reads the three files ──► ~/lab11 (your evidence)
```

The files are **synthetic**, generated by `data/genera_telemetria.py` (see
[Synthetic lab data](../DATI.md)). External addresses belong to the blocks reserved for
documentation (RFC 5737); users and company are made up. Field names are in English, as in real
formats. File names and the labels the commands print are Italian, as in the Italian version:
`rete` is network, `identita` identity, `falliti` failed, `esegue` runs, `scrive` writes, `fonte`
source and `cosa` what.

## Exercise

1. **What the network sees.** Each line of `rete.jsonl` is a flow: who talks to whom, on which
   port, for how long and how many bytes. Group the flows by source and duration:

   ```bash
   jq -r '"\(.src) \(.duration_s)s"' rete.jsonl | sort | uniq -c | sort -rn
   ```

   ```text
        24 203.0.113.45 1s
        12 198.51.100.23 1s
         1 203.0.113.45 188s
         1 10.0.0.21 1800s
   ```

   Two external addresses open dozens of one-second SSH connections, the pace of an automated
   tool. After 24 attempts, `203.0.113.45` gets a session lasting three minutes: most likely it
   got in. But as whom? Look at the sensor's fields:

   ```bash
   jq -sc 'map(keys) | add | unique' rete.jsonl
   ```

   ```text
   ["bytes_from_server","bytes_to_server","dport","dst","duration_s","proto","src","time"]
   ```

   No username and no command: SSH is encrypted, the network sees the envelope, not the letter.

2. **What identity sees.** The identity system records every attempt with the account and the
   result. Count the failures per source, and how many different accounts were tried:

   ```bash
   jq -sc 'map(select(.result == "failure")) | group_by(.src)[] | {src: .[0].src, falliti: length, account: (map(.user) | unique | length)}' identita.jsonl
   jq -r 'select(.result == "success") | "\(.time[11:19]) \(.user) da \(.src) con \(.method)"' identita.jsonl
   ```

   ```text
   {"src":"198.51.100.23","falliti":12,"account":12}
   {"src":"203.0.113.45","falliti":24,"account":1}
   02:12:01 deploy da 203.0.113.45 con password
   08:02:05 alice da 10.0.0.21 con publickey
   ```

   Now the two attacks have a name: `203.0.113.45` is a **brute force** (24 passwords on one
   account, `deploy`, successful in the end), `198.51.100.23` a **password spraying** (one
   attempt on each of 12 accounts, no success). But after the login the identity system goes
   quiet: it does not know what `deploy` did.

3. **What the endpoint sees.** The agent records the processes started, with their parent, and
   the files modified:

   ```bash
   jq -r '"\(.time[11:19]) \(.user // "-") \(.parent // .process) \(.command // "scrive \(.path)")"' endpoint.jsonl
   ```

   ```text
   02:12:02 deploy sshd -bash
   02:13:02 root sudo useradd -m -s /bin/bash svc-update
   02:13:02 - useradd scrive /etc/passwd
   02:13:02 - useradd scrive /etc/shadow
   02:13:40 root sudo usermod -aG sudo svc-update
   02:13:40 - usermod scrive /etc/group
   08:02:06 alice sshd -bash
   08:03:40 alice -bash vim /srv/app/config.yml
   ```

   At 02:12 `deploy` opens a shell; a minute later, with `sudo`, the `svc-update` account is
   created and added to the `sudo` group: that is **persistence**. The endpoint, though, does not
   see the 36 failed attempts, which never started a process, and does not know which address
   the session comes from. To it, the spraying never happened.

4. **The SIEM's view.** Merge the three sources into a single timeline, normalizing the records
   into three common fields: time, source and a description. Each file is recognized by a field
   only it has (`dport`, `result`, `type`). Show the two minutes around the login:

   ```bash
   jq -s -r 'map(
       if has("dport") then {time, fonte: "rete", cosa: "\(.src) -> \(.dst):\(.dport) per \(.duration_s)s"}
       elif has("result") then {time, fonte: "identita", cosa: "\(.user) da \(.src): \(.result)"}
       elif .type == "process" then {time, fonte: "endpoint", cosa: "\(.user) esegue \(.command)"}
       else {time, fonte: "endpoint", cosa: "\(.process) scrive \(.path)"} end)
     | sort_by(.time)[] | select(.time >= "2026-09-29T02:11:55Z" and .time < "2026-09-29T02:14:00Z")
     | "\(.time[11:19]) \(.fonte) \(.cosa)"' rete.jsonl identita.jsonl endpoint.jsonl
   ```

   ```text
   02:11:56 rete 203.0.113.45 -> 10.0.0.5:22 per 1s
   02:11:56 identita deploy da 203.0.113.45: failure
   02:12:01 rete 203.0.113.45 -> 10.0.0.5:22 per 188s
   02:12:01 identita deploy da 203.0.113.45: success
   02:12:02 endpoint deploy esegue -bash
   02:13:02 endpoint root esegue useradd -m -s /bin/bash svc-update
   02:13:02 endpoint useradd scrive /etc/passwd
   02:13:02 endpoint useradd scrive /etc/shadow
   02:13:40 endpoint root esegue usermod -aG sudo svc-update
   02:13:40 endpoint usermod scrive /etc/group
   ```

   Now the story is complete: **from where** (network), **who** (identity), **what they did**
   (endpoint). The links between the sources are address and time between network and identity,
   user and time between identity and endpoint. That is why clocks must be synchronized: with a
   minute of skew between sensors, this sequence would fall apart.

5. **A correlation rule.** A SIEM does not wait for someone to read the timeline: it applies
   rules that join the sources. This one flags a successful login after at least ten failures of
   the same account from the same address, and attaches the commands run with `sudo` in the
   following five minutes:

   ```bash
   jq -s -r --slurpfile ep endpoint.jsonl '
     . as $id | $id[] | select(.result == "success") | . as $ok
     | ($id | map(select(.result == "failure" and .user == $ok.user and .src == $ok.src and .time < $ok.time)) | length) as $falliti
     | select($falliti >= 10)
     | ($ok.time | fromdateiso8601) as $t
     | [$ep[] | select(.parent == "sudo" and ((.time | fromdateiso8601) - $t) >= 0 and ((.time | fromdateiso8601) - $t) <= 300) | .command] as $dopo
     | "ALLARME \($ok.time[11:19]) \($ok.user) da \($ok.src): accesso dopo \($falliti) falliti, poi con sudo: \($dopo | join("; "))"' identita.jsonl
   ```

   ```text
   ALLARME 02:12:01 deploy da 203.0.113.45: accesso dopo 24 falliti, poi con sudo: useradd -m -s /bin/bash svc-update; usermod -aG sudo svc-update
   ```

   A single alert, already carrying the context to decide: account compromised and persistence
   under way. None of the three sources could have written it alone. Save it with your evidence
   by running the command again with `> ~/lab11/allarme.txt` at the end.

6. **The visibility matrix.** Write in `~/lab11/matrice.md` a table with the incident's phases
   as rows (spraying, brute force attempts, successful login, shell, account creation, elevation
   to `sudo`) and the three sources as columns, marking each cell "sees", "sees in part" or
   "does not see", with the reason.

## Hints and solution

### Success indicators

- You told the two attacks apart: successful brute force from `203.0.113.45` on `deploy`,
  unsuccessful spraying from `198.51.100.23`.
- The timeline of step 4 shows, in order, the long flow, the successful login and the
  persistence commands.
- The rule of step 5 produces a single alert, with the two `sudo` commands.

### If you get stuck

Try on your own first: the hints open one at a time, from the vaguest to the solution.

<details>
<summary>Hint 1</summary>

`jq` reads a JSON Lines file one record at a time; to count or group you need all the records
together, in an array: that is what the `-s` (*slurp*) option does.

</details>

<details>
<summary>Hint 2</summary>

The timeline is empty or jumbled? The three sources have different fields: before sorting they
must be brought to the same schema, and time compared as an ISO 8601 string, which sorts
correctly only if every source uses the same format and the same time zone (here UTC, the `Z`).

</details>

<details>
<summary>Worked solution</summary>

The network sees the 36 attempts and the long session, but not the account or the commands,
because SSH is encrypted. Identity names the two attacks and the compromised account, but stops
at the login. The endpoint sees the persistence, but not the failed attempts or the source. Only
correlation, on address and time between network and identity and on user and time between
identity and endpoint, rebuilds the complete chain and allows a rule that raises an alert with
the context needed to respond. The response is the one from Lab 03: disable `svc-update`, reset
`deploy`, block the address, look for other changes.

</details>

### Common mistakes

- Concluding from the network alone that `203.0.113.45` got in "as root": the flow does not say
  which account.
- Considering the spraying harmless because the endpoint does not see it: no process does not
  mean no attack.
- Sorting the timeline without normalizing time formats, or with sensors in different time
  zones.
- Blaming `root` for creating the account without tracing back to the `deploy` session that
  started `sudo`.

## Final questions

1. Why does the network sensor not see the username, and what useful things does it see anyway?

   <details>
   <summary>Answer</summary>

   Because SSH encrypts the session, authentication included: the sensor sees only metadata,
   that is addresses, ports, duration and volumes. That is enough to recognize an automated tool
   (many short, identical connections), to notice the anomalous session that follows, and to see
   activity even from hosts with no agent or with their logs deleted.

   </details>

2. The EDR agent records `root` as the author of `useradd`. How do you trace it back to
   `deploy`?

   <details>
   <summary>Answer</summary>

   By following the process and session chain: `sudo` was launched from the shell `deploy`
   opened at 02:12:02, and `sudo` itself logs the user who invokes it. Real agents keep the
   session identifier and the parent process precisely for this: without them, attribution stops
   at the privileged account.

   </details>

3. Why does correlation depend on clock synchronization?

   <details>
   <summary>Answer</summary>

   Because the sources are joined on time: if the network sensor were two minutes ahead, the
   long session would appear after the commands it generated, and a rule with a five-minute
   window might no longer find them. That is why every source uses NTP and writes in UTC.

   </details>

4. The budget allows a single sensor. Which would you choose for this server, and what would you
   give up seeing?

   <details>
   <summary>Answer</summary>

   There is no single answer, but it must be justified: the endpoint sees the impact
   (persistence, changes) but not the attempts; identity sees who and how, useful against
   spraying and stolen credentials, but nothing after login; the network sees everything that
   passes, even from hosts without an agent, but not encrypted content. The choice often follows
   the main risk, compensated with preventive controls, such as SSH keys instead of passwords,
   which here would have made the brute force useless.

   </details>
