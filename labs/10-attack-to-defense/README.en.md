# Lab 10 — From trace to defense: reconnaissance and credential stuffing

| Field | Value |
|---|---|
| SY0-701 objectives | 2.4, 4.4, 4.5, 4.8 |
| Risk | `low` |
| Duration | 60 minutes |

You start from the recorded traces of two attacks on a web application, a reconnaissance run
looking for exposed files and a credential stuffing run against the login, and build the three
defensive answers: the rules that **detect** them, the configuration that **prevents** them and
the **response** actions. No attack is carried out: you work on synthetic logs and on a test
server listening only on your own computer.

## Scenario

Kestrelia's customer portal logged suspicious activity on September 29. The manager hands you
the web server log and the application's login log and asks for three things: understand what
happened, write the rules that would have flagged it in time, and prepare the reverse proxy
configuration that would have stopped it. Finally you propose the response for the account
involved.

## Prerequisites

- Linux, macOS or WSL with `awk`, `jq`, `curl` and `sha256sum`.
- nginx 1.19.5 or later for step 5 (`sudo apt install -y nginx` on Debian and Ubuntu,
  `brew install nginx` on macOS). The system service is not needed: the lab starts its own copy,
  in its own folder.
- The cloned repository: the traces are in `labs/10-attack-to-defense/data/`.
- Knowledge: indicators of attack (objective 2.4), monitoring and alerting (4.4), adjustable
  security controls such as web filters and limits (4.5) and incident response (4.8).

## Exercise

1. **An overview.** How many requests per address, and with what outcome:

   ```bash
   awk '{print $1, $9}' access.log | sort | uniq -c | sort -rn
   ```

   ```text
        39 198.51.100.50 401
         6 203.0.113.77 404
         6 10.0.0.21 200
         3 10.0.0.34 200
         2 198.51.100.50 200
         1 203.0.113.77 403
   ```

   Two external addresses stand out: one collects `404`s, the other `401`s, that is, denied
   sign-ins.

2. **The reconnaissance.** What `203.0.113.77` was looking for:

   ```bash
   awk '$1 == "203.0.113.77" {print substr($4, 14), $7, $9}' access.log
   ```

   ```text
   10:15:02 /.env 404
   10:15:05 /.git/config 404
   10:15:08 /backup.zip 404
   10:15:11 /config.php.bak 404
   10:15:14 /phpinfo.php 404
   10:15:17 /server-status 403
   10:15:20 /admin/ 404
   ```

   A list of files that should never be public (environment variables with secrets, git
   repositories, backups, diagnostic pages), one every three seconds: an automated tool. Here it
   found nothing, but the same run against a misconfigured server would expose credentials or
   code.

3. **The credential stuffing.** The application log shows which accounts were tried:

   ```bash
   jq -s '[.[] | select(.ip == "198.51.100.50")] | {tentativi: length, account_diversi: (map(.user) | unique | length), riusciti: [.[] | select(.result == "success") | .user]}' auth-events.jsonl
   ```

   ```text
   {
     "tentativi": 40,
     "account_diversi": 40,
     "riusciti": [
       "m.conti"
     ]
   }
   ```

   The keys are Italian, as in the Italian version: `tentativi` is attempts, `account_diversi`
   distinct accounts, `riusciti` successful. Forty accounts, one attempt each, one success: the
   mark of **credential stuffing**, which uses username and password pairs stolen in another
   breach and works when someone reuses the same password. What it did after signing in:

   ```bash
   grep '198.51.100.50' access.log | grep -v '/login'
   ```

   ```text
   198.51.100.50 - - [29/Sep/2026:10:32:10 +0000] "GET /account/export HTTP/1.1" 200 2457600 "-" "python-requests/2.32"
   ```

   Thirty seconds after signing in, a script downloaded the account's data export, about
   2.4 MB.

4. **Detection.** Two rules, written so a SIEM could apply them in real time. The first flags
   three requests for sensitive files from the same address ("ALLARME" is alert, "tre richieste a
   file sensibili" three requests for sensitive files):

   ```bash
   awk '$9 ~ /^40[34]$/ && $7 ~ /^\/(\.env|\.git|backup|phpinfo|server-status)|\.bak$/ {n[$1]++; if (n[$1] == 3) print "ALLARME", substr($4, 14), $1, "tre richieste a file sensibili"}' access.log
   ```

   ```text
   ALLARME 10:15:08 203.0.113.77 tre richieste a file sensibili
   ```

   The second flags ten failed sign-ins from the same address within 60 seconds, with a sliding
   window:

   ```bash
   jq -r 'select(.result == "failure") | "\(.time | fromdateiso8601) \(.ip) \(.time)"' auth-events.jsonl \
     | awk '{s[$2] = s[$2] " " $1; n = split(s[$2], a, " "); c = 0; for (i = 1; i <= n; i++) if ($1 - a[i] < 60) c++; if (c >= 10 && !visto[$2]++) print "ALLARME", $3, $2, c, "login falliti in 60 secondi"}'
   ```

   ```text
   ALLARME 2026-09-29T10:31:09Z 198.51.100.50 10 login falliti in 60 secondi
   ```

   The alert fires at 10:31:09, **thirty seconds before** the successful sign-in at 10:31:39.
   Detection works, but on its own it stops nothing: someone, or an automated playbook, must
   respond in under thirty seconds. Hence the next step.

5. **Prevention.** The reverse proxy in front of the application refuses hidden files and
   backups, and limits sign-ins to 5 a minute per address, with a tolerance (*burst*) of 3:

   ```bash
   cat > ~/lab10/nginx/nginx.conf <<'EOF'
   # Lab 10: prevenzione davanti all'applicazione (solo 127.0.0.1)
   pid nginx.pid;
   error_log error.log;
   events {}
   http {
     access_log access.log;
     limit_req_zone $binary_remote_addr zone=login:1m rate=5r/m;
     limit_req_status 429;
     server {
       listen 127.0.0.1:8090;
       location ~ /\. { return 404; }
       location ~* \.(bak|zip|sql|old)$ { return 404; }
       location = /login {
         limit_req zone=login burst=3 nodelay;
         try_files /dev/null @app;
       }
       location @app { return 401; }
       location / { return 200 "ok\n"; }
     }
   }
   EOF
   cd ~/lab10/nginx
   nginx -t -e error.log -p "$PWD/" -c nginx.conf
   nginx -e error.log -p "$PWD/" -c nginx.conf
   ```

   ```text
   nginx: the configuration file /home/your-user/lab10/nginx/nginx.conf syntax is ok
   nginx: configuration file /home/your-user/lab10/nginx/nginx.conf test is successful
   ```

   The `@app` location stands in for the application, which answers `401` to wrong credentials.
   Now repeat the reconnaissance and a stuffing attempt against the test server:

   ```bash
   for p in /.env /.git/config /backup.zip /; do
     printf '%s %s\n' "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8090$p)" "$p"
   done
   for i in $(seq 1 8); do curl -s -o /dev/null -w "%{http_code} " -X POST http://127.0.0.1:8090/login; done; echo
   ```

   ```text
   404 /.env
   404 /.git/config
   404 /backup.zip
   200 /
   401 401 401 401 429 429 429 429
   ```

   Sensitive files do not get out, even if someone left them in the public folder. After four
   attempts (one plus the burst of three) the address gets `429`: the forty attempts at 10:31
   would have stopped at the fourth. Stop the test server:

   ```bash
   nginx -e error.log -p "$PWD/" -c nginx.conf -s quit
   ```

6. **Response.** Write the playbook for the `m.conti` account in `~/lab10/response.md`, in
   order: end the active sessions and reset the password; tell the user their password is
   circulating elsewhere and must be changed wherever they reused it; treat the export as a
   possible personal data breach and involve the data protection officer; block both addresses;
   enable MFA on the portal and checks against passwords already seen in known breaches.

## Hints and solution

### Success indicators

- You separated the two attacks: `203.0.113.77` is reconnaissance, `198.51.100.50` successful
  credential stuffing against `m.conti`.
- The sign-in rule fires at 10:31:09, before the successful sign-in.
- The test server answers `404` for sensitive files and `429` from the fifth sign-in attempt.

### If you get stuck

Try on your own first: the hints open one at a time, from the vaguest to the solution.

<details>
<summary>Hint 1</summary>

The web server log does not contain usernames: to know which accounts were tried you need the
application log, `auth-events.jsonl`.

</details>

<details>
<summary>Hint 2</summary>

The nginx limit does not kick in? If the `/login` location answers directly with `return`, the
response is sent before `limit_req` is evaluated: the request must go through an internal
location, such as `@app`, or a `proxy_pass` to the application.

</details>

<details>
<summary>Worked solution</summary>

Reconnaissance shows as a list of sensitive paths requested in sequence by an automated client;
credential stuffing as many accounts, one attempt each, and one success. Detection arrives in
time, but on its own it does not break the attack. Prevention at the reverse proxy stops it
earlier: no hidden files or backups served, and a per-address limit on sign-ins. An attack spread
over many addresses also needs MFA and checks against breached passwords. The response covers
the compromised account and the exported data, not just the addresses.

</details>

### Common mistakes

- Calling credential stuffing a brute force: here each account gets a single attempt, with
  credentials the attacker already has.
- Using `return` in the limited location: `limit_req` is never applied.
- Relying only on the per-address limit: an attack spread over many addresses gets around it.
- Blocking the addresses and forgetting the export: `m.conti`'s data has already left.

## Final questions

1. What is the difference between credential stuffing, password spraying and brute force?

   <details>
   <summary>Answer</summary>

   **Brute force** tries many passwords against one account. **Password spraying** tries a few
   common passwords against many accounts. **Credential stuffing** tries known username and
   password pairs, stolen elsewhere: one attempt per account, and it works only where the
   password was reused. That is why the most effective defense against stuffing is MFA, together
   with checks against passwords already seen in breaches.

   </details>

2. The sign-in rule fires thirty seconds before the successful sign-in. Why was it not enough?

   <details>
   <summary>Answer</summary>

   Because an alert is information, not action: if nobody, and no automated playbook, blocks
   the address or the account within those thirty seconds, the attack goes on. A detective
   control must always be paired with a preventive control or an automated response.

   </details>

3. The reverse proxy answers `404` for `/.env` even though the file does not exist. What is it
   for?

   <details>
   <summary>Answer</summary>

   It protects against future mistakes: if someone one day copied a `.env` file or a backup into
   the public folder by accident, the proxy would still not serve it. It is defense in depth
   applied to configuration.

   </details>

4. Which obligations can the export of `m.conti`'s data trigger?

   <details>
   <summary>Answer</summary>

   If it contains personal data, it is a breach to assess under the applicable law, for example
   the GDPR for a European company: document it, assess the risk to the person and, where
   required, notify the authority and the data subject within the set deadlines. The decision
   belongs to the organization and its data protection officer, but gathering the evidence
   starts in the incident response.

   </details>
